# 2026-06-11 — `pomodoro-overtime-fullscreen` (attempt 2)

## Fullscreen overtime screen + heads-up end-of-session notification

When a Pomodoro session's timer crosses zero, the app now:
opens a fullscreen lock-screen-aware activity (visually similar
to the Android Clock app's timer end-screen), vibrates, plays the
device's default **alarm** ringtone, and posts a heads-up
notification that mirrors the activity's negative time. The
timer keeps running into negative values (`−00:07`, `−00:08`, …)
until the user taps **+ 1:00** (returns the timer to a positive
value) or **Stop** (ends the session).

### Attempt 2 — what changed and why

The first attempt was rejected by the verifier because three
different code paths each recorded a database row on a single
session end:

1. `PomodoroTimerService.handleEngineState` emitted a
   `PomodoroAlarmEvent.SessionComplete` to the event bus when
   the engine crossed zero.
2. `PomodoroAlarmReceiver.onReceive` did the same when
   `AlarmManager` fired (with a few seconds of jitter relative
   to the engine's tick).
3. `PomodoroViewModel.syncUiFromEngine` called
   `handleSessionCompleteOvertime` on the same negative
   transition.

Plus the receiver posted a stale `CATEGORY_ALARM` "Time for a
break" notification that the new fullscreen flow had made
obsolete. Net result: one completed Pomodoro produced **three
DB rows** and a confusing notification pair.

This attempt reworks the data path so the **engine state is the
single source of truth**:

- The `PomodoroEventBus` and `PomodoroAlarmEvent` classes are
  deleted entirely. Nothing in the codebase references them
  anymore.
- The receiver is now a **UX-only** hook. It checks the engine
  state (so it is a no-op if the service has already handled
  the session end) and fires the same vibrate / ringtone /
  overtime-heads-up / launch-activity as the service would. It
  no longer posts the legacy "Time for a break" notification
  and no longer emits a `SessionComplete` event.
- The service's `handleEngineState` no longer emits a
  `SessionComplete` event. It only does the UX side-effects.
- The ViewModel observes the engine state directly and writes
  **exactly one** row on the first transition from
  `remainingMillis >= 0L` to `remainingMillis < 0L`, gated by
  an `overtimeRecorded: Boolean` field that is reset by
  `onStart` / `onReset` / `onPresetSelected`. The
  `eventCollectionJob` and `handleAlarmSessionComplete`
  methods are deleted.
- A new `PomodoroSessionEndSignal` `@Singleton` is shared
  between the receiver and the service so they don't both
  fire the UX on a single session end (the alarm-vs-engine
  race can fire both within a few seconds of each other). The
  first caller wins; the second sees a recent timestamp and
  skips. A 10s window absorbs the race without swallowing a
  legitimate re-fire after `+1:00`.

### State-machine transition table (corrected)

| step | action | status | remainingMillis | what records to DB | what fires UX |
|------|--------|--------|------------------|---------------------|---------------|
| 1    | start  | RUNNING | `25*60_000L`     | nothing (yet)       | nothing       |
| 2    | tick   | RUNNING | `25*60_000L - N*1_000L` | nothing | nothing |
| 3    | tick   | RUNNING | `0L`             | nothing (transition not yet fired) | nothing |
| 4a   | engine ticks to `-1_000L` | RUNNING | `-1_000L` | **ViewModel:** `overtimeRecorded` was `false` → set to `true` → `handleSessionCompleteOvertime` writes **row #1**. | **Service:** `sessionEndSignal.tryFire()` returns `true` → vibrate, ringtone, launch activity. |
| 4b   | alarm fires | RUNNING | `-2_000L` | nothing (already recorded) | **Receiver:** `sessionEndSignal.tryFire()` returns `false` → no-op. **No double-fire.** |
| 5    | +1:00  | RUNNING | `58_000L`        | nothing             | service: `sessionEndSignal.reset()` |
| 6    | tick   | RUNNING | `0L`             | nothing (transition fires only on first crossing of 0 per session) | nothing |
| 7    | tick   | RUNNING | `-1_000L`        | nothing — `overtimeRecorded` is still `true` from step 4a, so the second crossing does **not** write a second row | service: `sessionEndSignal.tryFire()` returns `true` (window expired) → vibrate, ringtone, launch activity |
| 8    | stop   | IDLE   | `0L`             | nothing (session was already recorded in 4a) | service: `stopForegroundCompat`, `ringtonePlayer.stop`, `stopSelf` |
| 9    | start next session | IDLE→RUNNING | `next duration` | `overtimeRecorded = false` reset by `onStart` | `sessionEndSignal.reset()` |

### Concurrency invariants

For every planned session the system writes **exactly one**
`PomodoroSession` row to the database. The two guards that
enforce this:

1. `PomodoroViewModel.overtimeRecorded` is a per-session
   boolean. The DB write happens only on the first transition
   from `remainingMillis >= 0L` to `< 0L` (the `inOvertime &&
   !overtimeRecorded` test inside `syncUiFromEngine`).
2. The viewmodel never calls `recordSessionInBackground` from
   any other path. `handleAlarmSessionComplete` is gone.

For every session end the user sees the vibrate / ringtone /
activity launch / heads-up notification **exactly once**. The
two dedup mechanisms:

1. `PomodoroSessionEndSignal.tryFire()` is an atomic CAS on a
   `lastFiredAtMillis` field with a 10s dedup window. The
   service and the receiver both call it; the first caller
   wins; the second caller (if any) returns early.
2. The receiver's state check (`engine.state.value.status ==
   RUNNING` + `sessionType` match + `remainingMillis >= 0L`)
   is a redundant safety net — if the engine has already
   gone negative and the service fired, the receiver is a
   no-op even before the signal CAS.

### Manual test plan (re-issued)

1. **Start a 25-min focus session** from the Pomodoro screen.
2. **Let the timer hit zero**. The activity launches
   automatically, vibrates, and the default alarm ringtone
   starts looping every 2 s. The heads-up notification shows
   `−00:00` / `−00:01` / … with the actions `Stop` and
   `Add 1 min`. The in-app screen (if brought forward) shows
   the same negative time in the timer ring. The user feels
   the vibration **once** and hears the ringtone start
   **once**.
3. **Tap `+ 1:00`** in the activity (or in the notification
   action). The timer jumps to `00:01` and counts up. The
   planned-end alarm is re-armed to the new (later) zero
   point.
4. **Let the timer hit zero again** (or wait the
   re-armed interval). The user feels a second vibration
   and the ringtone starts a second time, the activity is
   re-launched, the heads-up notification is re-posted —
   but **the database gets no new row** (the
   `overtimeRecorded` flag is still `true`).
5. **Tap `Stop`**. The activity finishes itself, the
   notification is cleared, the service stops, the ringtone
   stops, and the Pomodoro screen returns to idle.
6. **Background the app** first, then let the timer hit zero.
   Confirm: the activity launches over the lock screen and
   `requestDismissKeyguard` makes the device unlock.
7. **Quick test path**: temporarily change
   `PomodoroPreset.Classic.focusMinutes` to `1` in
   `domain/model/PomodoroPreset.kt`, install the debug APK,
   start a session, wait 60 s — confirm the full overtime
   flow works end-to-end.

### Verification — DB write count

Before the fix (rejected attempt): the verifier observed
**three** rows per session end. The cause was three writers
emitting the "session ended" signal: receiver → bus → VM,
service → bus → VM, VM engine-state detection.

After the fix: the only writer is the ViewModel, gated by
`!overtimeRecorded`. **One** row per planned session.
